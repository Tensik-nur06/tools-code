Что это вообще такое?

🤔 В двух словах

Это «мозг» (backend) веб-сайта для обучения кибербезопасности. Сайт — это то, что видит пользователь в браузере (HTML, картинки, кнопки). Backend — это то, что скрыто на сервере: база данных, логика, безопасность.

📊 Что делает backend в нашем проекте?

  • Хранит данные — пользователей, курсы, оценки в базе данных PostgreSQL
  • Проверяет безопасность — когда пользователь вводит пароль, backend проверяет его через хеш
  • Выдает JWT токены — уникальные ключи доступа вместо пароля при каждом запросе
  • Рассчитывает XP — добавляет опыт, когда пользователь завершает урок
  • Контролирует доступ — админ может что-то, обычный пользователь не может
  • Возвращает данные — отправляет информацию фронтенду через API

⚙️ Какие технологии используются?

Технология Для чего Простое объяснение
Python Язык программирования На нём написан весь код backend'а. Populярный для начинающих
FastAPI Веб-фреймворк Фреймворк для создания API. На него опирается весь код
PostgreSQL База данных Хранилище с таблицами. Как большой Excel где хранятся юзеры и курсы
SQLAlchemy ORM (объектно-реляционная модель) Промежуточник между Python кодом и БД. Переводит код на SQL
JWT Аутентификация Токены доступа. Каждый запрос содержит уникальный ключ
💡 Совет: Не нужно понимать всё сразу. Эти технологии связаны между собой. Когда мы пройдем пример регистрации, всё станет понятно.

🎯 Ключевые файлы, которые нужно понимать

1. main.py — Точка входа

Это центр управления. Здесь создается приложение FastAPI, подключаются все routes (адреса), настраивается CORS для безопасности. Когда ты запускаешь сервер — запускается в первую очередь этот файл.

2. config.py — Все настройки в одном месте

Здесь указываются: адрес БД, SECRET_KEY для JWT, время жизни токена, список разрешённых сайтов (CORS). Если что-то не работает — часто нужно менять это.

3. database.py — Подключение к PostgreSQL

Здесь создается connection к базе данных. Функция get_db() предоставляет сессию для каждого запроса.

4. models/user.py, course.py, lesson.py — Таблицы БД

Каждый файл определяет одну таблицу. Например, user.py определяет структуру пользователя: какие поля есть (email, пароль, XP), какие ограничения.

5. api/endpoints/auth.py — Маршруты регистрации/логина

Здесь два главных endpoint: /register (создать аккаунт) и /login (получить токен). На эти адреса фронтенд отправляет запросы.

Как работает база данных?

📋 Что такое таблица?

База данных PostgreSQL — это как большой Excel файл с таблицами. Каждая таблица хранит один тип данных.

👥 Таблица Users (пользователи)

Колонка Тип Объяснение Примеры
id Integer (ключ) Уникальный номер каждого пользователя 1, 2, 3, ...
email String Email адрес (уникальный) user@example.com
username String Имя пользователя (уникальное) john_doe, hacker123
hashed_password String Зашифрованный пароль (НЕ открытый!) $2b$12$abc...xyz (bcrypt хеш)

Колонка Объяснение

  • id — уникальный номер урока

Как работает регистрация/логин? (Жизненный цикл)

🔄 Полный цикл: от регистрации до получения токена

Шаг 1: Пользователь заполняет форму регистрации

На фронтенде (HTML/JS) пользователь вводит:

email: "john@example.com" username: "john_doe" password: "SecurePass123" full_name: "John Doe"
Шаг 2: Фронтенд отправляет POST запрос

JavaScript отправляет эти данные на адрес http://localhost:8000/api/v1/auth/register

Шаг 3: Backend получает данные

Код в api/endpoints/auth.py ловит этот запрос в функции register()

Шаг 4: Валидация (проверка)

Backend проверяет:

  • Email валиден (содержит @)
  • Email не используется (уникальный)
  • Пароль достаточно сильный (8+ символов, заглавная буква, цифра)
  • Username уникален
Если что-то не так — отправляет ошибку 400 (Bad Request)

Шаг 5: Хеширование пароля

Backend НЕ сохраняет открытый пароль! Вместо этого:

  • Берет пароль "SecurePass123"
  • Превращает его в хеш через bcrypt: $2b$12$abc...xyz (очень длинная строка)
  • Сохраняет в БД только хеш
Важно: Хеш нельзя обратно превратить в пароль. Это односторонняя функция!

Шаг 6: Запись в БД

Backend вставляет новую запись в таблицу users:

INSERT INTO users (email, username, hashed_password, full_name, level, xp, created_at) VALUES ('john@example.com', 'john_doe', '$2b$12$abc...xyz', 'John Doe', 1, 0, NOW())
Шаг 7: Возврат профиля фронтенду

Backend отправляет обратно созданного пользователя (БЕЗ пароля!)

{ "id": 1, "email": "john@example.com", "username": "john_doe", "full_name": "John Doe", "level": 1, "xp": 0, "created_at": "2026-04-06T10:30:00" }

🔑 Теперь логин (вход в аккаунт)

Шаг 1: Пользователь вводит email и пароль
email: "john@example.com" password: "SecurePass123"
Шаг 2: Фронтенд отправляет POST на /api/v1/auth/login
Шаг 3: Backend ищет пользователя по email
SELECT * FROM users WHERE email = 'john@example.com';

Если не найден — ошибка 401 (Unauthorized)

Шаг 4: Backend сравнивает пароли

Backend берет введенный пароль "SecurePass123" и сравнивает с хешированным паролем из БД используя bcrypt.verify(). Если не совпадает — ошибка 401.

Шаг 5: Создание JWT токена

Если пароль правильный, backend создает JWT токен. Это длинная строка которая содержит:

  • ID пользователя
  • Время создания
  • Время истечения (через 30 минут)
  • Все это зашифровано SECRET_KEY
Пример: eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiIxIiwiZXhwIjoxNjExOTI3MjAwfQ.abc...

Шаг 6: Возврат токена фронтенду

Backend отправляет:

{ "access_token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...", "refresh_token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...", "expires_in": 1800 }
Шаг 7: Фронтенд сохраняет токен

JavaScript сохраняет access_token в localStorage (локальное хранилище браузера)

📡 Теперь каждый запрос пользователя

Когда пользователь хочет получить свой профиль:

Фронтенд отправляет запрос на GET /api/v1/auth/me с заголовком:

Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...
Backend проверяет токен

Функция get_current_user() в api/deps.py:

  • Извлекает токен из заголовка
  • Проверяет подпись (не подделан ли)
  • Проверяет не истекло ли время жизни
  • Если все ок — извлекает ID пользователя
Если токен невалиден — ошибка 401

Backend возвращает данные

Если токен валиден, backend получает ID из токена, ищет пользователя в БД и отправляет его профиль.

💡 Понимание токенов: JWT токен — это как билет в кино. Билет подписан кино-театром (зашифрован SECRET_KEY). Портной не может подделать билет, потому что не знает подпись. Когда ты входишь — театр проверяет подпись, смотрит что билет валидный, и пускает тебя.

Безопасность: пароли и токены

🔐 Почему нельзя хранить пароли в открытом виде?

Если база данных утечет, злоумышленник получит все пароли. Поэтому пароли нужно хешировать.

🔒 Что такое bcrypt?

bcrypt — это функция, которая превращает пароль в невозможно-угадаемый хеш:

Открытый пароль: "MySecurePassword123" Bcrypt хеш: "$2b$12$R9h7cIPz0gi.URNNX3kh2OPST9/PgBkqquzi.Ss7KIUgO2t0jKMUm" Хеширование ОДНОСТОРОННЕЕ: пароль → хеш ✅ хеш → пароль ❌ (невозможно)

Почему bcrypt хорош?

  • Соль (salt) — каждый хеш содержит случайное число, поэтому один пароль имеет разные хеши
  • Медленный — это хорошо, потому что замедляет перебор паролей
  • Стандарт — используется везде

🔑 Как работает проверка пароля?

При регистрации:
  1. Пользователь вводит: "MySecurePassword123"
  2. backend вызывает: bcrypt.hash("MySecurePassword123")
  3. Получается: "$2b$12$R9h7cIPz0gi.URNNX3kh2..."
  4. Это сохраняется в БД
При логине:
  1. Пользователь вводит: "MySecurePassword123"
  2. backend достает хеш из БД: "$2b$12$R9h7cIPz0gi.URNNX3kh2..."
  3. backend вызывает: bcrypt.verify("MySecurePassword123", "$2b$12$...")
  4. Если совпадает → ✅ ОК, иначе → ❌ Ошибка

🎫 JWT токены

JWT (JSON Web Token) — это цифровой пропуск, который выдается при логине. Вместо того чтобы отправлять пароль при каждом запросе, фронтенд отправляет токен.

📦 Структура JWT токена

eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9 ↓ {"alg":"HS256","typ":"JWT"} (Заголовок - говорит как зашифровано) . eyJzdWIiOiI1IiwiZXhwIjoxNzE3NjU3NjAwfQ ↓ {"sub":"5","exp":1717657600} (Payload - данные: ID пользователя и время истечения) . SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c ↓ (Подпись - зашифровано SECRET_KEY) Формат: header.payload.signature

🔐 Как backend проверяет токен?

  • Извлекает токен из заголовка Authorization
  • Разбивает на части: header.payload.signature
  • Пересчитывает подпись с SECRET_KEY
  • Сравнивает пересчитанную подпись с полученной
  • Если совпадает → токен валиден
  • Проверяет время истечения (exp)
  • Если все ОК → извлекает его данные (ID пользователя)

⏰ Время жизни токена

Токен Время жизни Назначение
Access Token 30 минут Для обычных запросов. Короткий — для безопасности
Refresh Token 7 дней Для получения нового Access Token без пароля

🔄 Как обновить токен?

Когда access token истекает (через 30 минут), пользователь может отправить refresh token на endpoint /api/v1/auth/refresh и получить новый access token БЕЗ ввода пароля.

💡 Аналогия: JWT — это как пропуск на некую территорию. Пропуск действует 30 минут. Если пропуск истекает, охранник говорит "Поищи механизм у входа (refresh token), и он выдаст тебе новый пропуск". Это лучше, чем каждый раз вводить пароль.

Геймификация: XP, уровни и бейджи

🎮 Что такое геймификация?

Добавление игровых элементов (очки, уровни, достижения) чтобы сделать обучение веселее и мотивировать пользователей.

⭐ XP (Experience Points)

XP — это опыт, который пользователь получает за завершение уроков.

Действие XP
Завершить урок (базовое значение) 100 XP
Идеальный скор (100%) +50 бонус XP
Получить бейдж +500 бонус XP

📈 Уровни

Уровень повышается когда пользователь набирает достаточно XP. Каждый уровень требует 1000 XP.

Уровень Нужно XP Статус
1 0-999 Новичок
2 1000-1999 Ученик
3 2000-2999 Адепт
4 3000-3999 Мастер
5+ 4000+ Легенда

Пример:

  • Пользователь завершает первый урок → получает 100 XP (всего 100)
  • Завершает 10 уроков → 100*10 = 1000 XP → поднял уровень на 2! 🎉
  • Завершает еще 10 уроков → 2000 XP → уровень 3!
# Как это рассчитывается в коде level_progress = 5 * 1000 # Уровень 5 требует 5000 XP if user.xp >= 5000: user.level = 5 print("Поздравляем, вы достигли 5 уровня! 🎉")

Частые ошибки и как их исправить

❌ Ошибка: "Cannot connect to database"

Причина: Нет подключения к PostgreSQL или неправильно указан адрес в .env

Решение:

  • Проверить что PostgreSQL запущена: psql --version
  • Проверить что БД создана: psql -U postgres -l | grep cybersecurity_lms
  • Проверить DATABASE_URL в .env файле
  • Убедиться что пароль правильный

❌ Ошибка: "ModuleNotFoundError: No module named 'fastapi'"

Причина: Виртуальное окружение не активировано или зависимости не установлены

Решение:

# 1. Активировать окружение venv\Scripts\activate # Windows source venv/bin/activate # Linux/Mac # 2. Установить зависимости pip install -r requirements.txt

❌ Ошибка: "Port 8000 already in use"

Причина: Другой процесс использует порт 8000

Решение:

# Вариант 1: Остановить существующий сервер (Ctrl+C) # Вариант 2: Использовать другой порт uvicorn app.main:app --reload --port 8001

❌ Ошибка: "Invalid email or password" при логине

Причина: Email не найден в БД или пароль неправильный

Решение:

  • Убедиться что вы зарегистрировались (произошла ошибка при регистрации?)
  • Проверить что email написан правильно (точные прописные буквы)
  • Проверить что пароль правильный
  • Проверить в БД напрямую: psql -U lms_user -d cybersecurity_lms -c "SELECT email FROM users;"

❌ Ошибка: "1 validation error for UserRegisterRequest"

Причина: Невалидные данные при регистрации

Решение:

Проверить требования к полям:

  • email: Должен быть email (содержать @)
  • username: 3-50 символов, только буквы/цифры/_
  • password: минимум 8 символов, заглавная буква, цифра

❌ Ошибка: "401 Unauthorized" при запросе с токеном

Причина: Токен истек вышел, невалиден или забыли ввести

Решение:

  • Проверить что токен передан: Authorization: Bearer {token}
  • Получить новый токен: выполнить логин еще раз
  • Проверить что SECRET_KEY не изменился (иначе все токены станут невалидными)

❌ Ошибка: "CORS error" при запросе с фронтенда

Причина: Frontend попытался обратиться с запрещённого домена

Решение:

Добавить домен в ALLOWED_ORIGINS в .env или config.py:

# .env ALLOWED_ORIGINS=http://localhost:3000,http://localhost:8080,https://example.com

❌ Ошибка: "table users does not exist"

Причина: Таблицы не были автоматически созданы

Решение:

Backend создает таблицы автоматически при запуске. Если ошибка — проверить логи:

# При запуске сервера должно быть ✅ Database tables initialized # Если не видите — BД может быть пустой # Проверить: psql -U lms_user -d cybersecurity_lms -c "\dt"

💡 Общие советы при ошибках

  1. Читай логи! Сервер выводит подробные логи — они раскажут в чем ошибка
  2. Проверь конфиг — 80% ошибок из-за неправильного .env
  3. Перезагрузись — иногда помогает остановить сервер (Ctrl+C) и запустить заново
  4. Проверь БД — если сомневаешься, смотри прямо в postgresql
  5. Поищи в коде — текст ошибки часто есть в коде (помогает понять что случилось)
